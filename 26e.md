## OBSERVED / INFERRED / UNPROVEN (as of 2026-08-16)

### Observed
- `scripts/pi4-image-build.sh` default manifest is `configs/root_task_pi4_uboot_aarch64.toml` (`line 11`).
- For `.toml` manifests, build flow calls `run_coh_rtc_codegen` before compilation (`line 1642`) and passes:
  - manifest path `$MANIFEST_PATH`
  - `--manifest "$GENERATED_CONFIG_DIR/root_task_resolved.json"`
  - `--out apps/root-task/src/generated`.
- `run_coh_rtc_codegen_for_manifest` executes `cargo run -p coh-rtc -- "$manifest_path" --out ... --manifest ...`.
- `coh-rtc` load step parses the manifest directly (`load_manifest`) with no profile alias rewrite in this path.
- Root-task generation emits both:
  - `configs/generated/root_task_resolved.json`
  - `configs/generated/root_task_topology.json` (derived sibling path from `root_task_resolved.json`).
- `main()` in `pi4-image-build.sh` sets `RESTORE_CANONICAL_CODEGEN=1` when selected manifest differs from canonical (`line 2745`).
- `cleanup` runs on exit (`trap cleanup EXIT` in `main`) and restores canonical outputs via `run_coh_rtc_codegen_for_manifest` using `CANONICAL_MANIFEST_PATH` (`line 1523`).
- Pi manifest is explicitly `pi4-uboot-aarch64`; `apps/root-task/src/generated/bootstrap.rs` currently contains that profile value in `INITIAL_AUDIT_LINES`.
- Current checked-in generated topology/resolved JSON under `configs/generated/*` still report `virt-aarch64`.

### Inferred
- A normal Pi build invocation does generate Pi layout tables into generated outputs before compilation; canonical restore happens **after** build/compile steps.
- Therefore, the `virt-aarch64` values in `configs/generated/*` are likely post-build canonical restore artifacts, not a pre-build input override for the Pi compile.
- This mismatch by itself is not yet causally proven for the physical receive-cap fault at CPtr `0x5b`.

### Unproven
- Exact meaning of faulting CPtr `0x5b` (which capability/object slot it should reference) in this rootserver binary.
- Whether the receive-cap fault is directly caused by profile mismatch versus another root-task bootstrap ordering/invariant fault.
- Whether the current failing physical image was guaranteed to be built from this exact workspace state versus older staged content.
- `0x5b` maps to which allocated object in root fault/control allocation tables after applying this one-line diagnostic build.
