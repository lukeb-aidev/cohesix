# Hardware Bring-up (As-Built)

## Scope
- Cohesix supports two bring-up paths:
  - QEMU `aarch64/virt` (development/CI baseline).
  - Raspberry Pi 4 (`bcm2711`) via upstream-style boot chain: `Pi firmware -> U-Boot -> seL4 image -> root-task`.
- Milestone 26 defines the strict no-NIC baseline on Pi 4; Milestone 26a adds profile-gated GENETv5 + static IPv4; the historical 26b compatibility baseline adds the interactive U-Boot policy wizard, DTB `/chosen/cohesix,*` network-policy handoff, Cohesix-owned xHCI/VL805 local-seat cold start, wired DHCP, and the staged Pi 4 Wi-Fi runtime path. Reopened 26a/26b driver-task closure is not as-built until fresh captures prove dedicated driver-task isolation for the active hardware paths.

## Canonical Pi 4 boot chain
1. Pi boot firmware loads `start4.elf` and `fixup4.dat`.
2. Firmware loads `u-boot.bin` (from FAT boot partition).
3. U-Boot loads the staged Cohesix payload (`cohesix-image-arm-bcm2711`) and the padded staged Pi 4 DTB (`bcm2711-rpi-4-b.dtb`) using `fatload`.
4. U-Boot applies any saved/runtime Cohesix policy into DTB `/chosen/cohesix,*`, quiesces the USB host stack, and transfers control with `bootm`.
5. seL4 enters root-task; Cohesix reaches `cohesix>` prompt.

## Manifest profiles
- Development profile: `configs/root_task.toml` (`profile.name = "virt-aarch64"`).
- Pi 4 U-Boot profile: `configs/root_task_pi4_uboot_aarch64.toml` (`profile.name = "pi4-uboot-aarch64"`). This is the current Pi 4 baseline used by `scripts/pi4-image-build.sh`.
- Legacy migration alias: `configs/root_task_uefi_aarch64.toml` (`profile.name = "uefi-aarch64"`). Do not treat this file as the current Pi 4 hardware baseline.
- `coh-rtc` enforces profile gates:
  - Milestone 26 baseline: `hw.no_nic=true`, `features.net_console=false`.
  - Milestone 26a/26b networking: `hw.network.enabled=true`, `hw.network.backend=bcmgenet-v5`, bounded `hw.network.mode` (`off|static|dhcp`), bounded `hw.network.interface` (`wired|wifi|auto`), DHCP retry/timeout bounds, required `net` device declaration, and bounded non-zero static IPv4 (`prefix_len=1..32`) when `mode=static`.
  - declared `uart` + `rtc` devices
  - local-seat declarations when `hw.local_seat.enabled=true`
  - attestation policy/device requirements when `hw.attestation.enabled=true`

## Pi 4 build + boot commands
1. Build seL4 Pi 4 image:
`scripts/pi4-image-build.sh --manifest configs/root_task_pi4_uboot_aarch64.toml`
2. Build U-Boot (Pi 4):
`make -C third_party/u-boot rpi_4_defconfig`
`make -C third_party/u-boot CROSS_COMPILE=aarch64-linux-gnu- -j$(sysctl -n hw.ncpu)`
3. For a full clean Pi 4 rebuild, use:
`scripts/pi4-image-build.sh --clean --manifest configs/root_task_pi4_uboot_aarch64.toml`
- `--clean` removes `root-task` Cargo artifacts, cleans and rebuilds the Pi 4 seL4 U-Boot build tree, and runs a fresh `rpi_4_defconfig` U-Boot rebuild before staging/flashing.
- On macOS ARM64, `--clean` also injects the Homebrew OpenSSL include/lib paths into the U-Boot host-tool build so `mkimage` and the other host utilities rebuild against the expected OpenSSL installation.
- `scripts/pi4-image-build.sh` validates that the external seL4 Pi 4 overlay and any generated `kernel/kernel.dts` expose `device-untypes@600000000` for the VL805 BAR0 window. It refuses to patch seL4 kernel sources during proof runs; missing device-untyped coverage must be fixed intentionally in the external seL4 tree and then rebuilt.
- `scripts/pi4-image-build.sh` builds the root task with `release-pi4,bootstrap-trace` by default, strips only the root-task ELF copy injected into the seL4 archive, and keeps the flashed rootfs CPIO under `scripts/ci/size_guard.sh` while leaving the normal Cargo artifact available for local symbol inspection.
- Runtime serial probing on the Pi 4 U-Boot path prefers the mini-UART
  (`serial1`) path used by the staged image; PL011 is QEMU/dev-path language
  unless an explicit fallback profile declares it. A trace that stops immediately after
  `cold-boot keyboard probe end stage=pre-net` is treated as a UART-selection
  blocker until the next image shows `[uart] runtime init begin/end`.
4. Prepare FAT boot partition with:
- Pi firmware files (`start4.elf`, `fixup4.dat`, required DTB/overlay files),
- `u-boot.bin`,
- `cohesix-image-arm-bcm2711` (copied from seL4 `images/sel4test-driver-image-arm-bcm2711`),
- Cohesix U-Boot assets (`boot.scr.uimg`, `boot.cmd`, `config.txt`, `cohesix-driver-runtimes.cpio.uimg`, optional HDMI logo bitmaps, and Linux Wi-Fi debug helpers).
5. Ensure `config.txt` includes:
- `arm_64bit=1`
- `enable_uart=1`
- `kernel=u-boot.bin`
- `dtoverlay=upstream-pi4`
- `core_freq=250` (keeps UART handoff deterministic during firmware -> U-Boot transition)
6. Boot from U-Boot shell:
- `fatls mmc 0:1`
- `fatload mmc 0:1 ${loadaddr} cohesix-image-arm-bcm2711`
- `fatload mmc 0:1 0x15000000 cohesix-driver-runtimes.cpio.uimg`
- `fatload mmc 0:1 0x14000000 bcm2711-rpi-4-b.dtb`
- `bootm ${loadaddr} 0x15000000 0x14000000`

## U-Boot networking setup (for 26a/26b prep)
- The current Pi 4 manifest defaults to DHCP with `interface=auto` and requires the local-seat path: without saved U-Boot policy or Wi-Fi credentials it selects GENET/wired DHCP, while explicit wizard/DTB policy can select Wi-Fi DHCP once credentials are provided. HDMI/USB failures are no longer silent on the Pi 4 profile; required local-seat declaration failures remain fatal, but runtime backend attach failures degrade with `required=yes action=serial-shell` so the UART root shell stays reachable for recovery. A present backend with a keyboard that is not ready on the first bounded probe keeps polling instead of falling back to serial-only. The U-Boot wizard plus persisted `cohesix.env` policy handoff still flows through a staged padded DTB and U-Boot `bootm`, with manifest defaults authoritative when the handoff is absent or invalid.
- Typical env setup:
- `setenv autoload no`
- `setenv ipaddr <board-ip>`
- `setenv serverip <host-ip>`
- `setenv ethact <interface>`
- The staged `boot.cmd` now presents a Linux-style numbered wizard over the existing U-Boot consoles:
- `Continue with existing config` is the default action when saved Cohesix policy already exists in `cohesix.env`.
- `Boot with manifest defaults` is the default action when no saved Cohesix overrides exist.
- `Configure networking` walks DHCP `ON|OFF`, `wired|wifi`, Wi-Fi credentials when needed, and static IPv4 prompts only when DHCP is off.
- `Save current settings and reboot` persists only the user-facing Cohesix policy fields to `cohesix.env` on the FAT boot partition; it does not rewrite the manifest or generic U-Boot environment.
- The wizard intentionally uses `askenv`-based numbered prompts instead of U-Boot `bootmenu`, because upstream U-Boot documents `bootmenu` as an ANSI-terminal path and the simpler prompt flow is more reliable on the Pi 4 HDMI + USB-keyboard bring-up path while still preserving serial control via `minicom`.
- The script reloads only `cohesix.env` from the FAT partition and keeps the PREBOOT console serial-first. The default staged wizard bootstraps menu/input USB with `pci enum; usb start` and switches `stdin` to `usbkbd,serial` after that session is live so the HDMI wizard keeps USB keyboard input; pass `--uboot-menu-input serial` only for serial-only lab captures that need the fastest handoff. The menu no longer emits the old bring-up-only USB diagnostic snapshots or the extra USB diagnostics submenu; the runtime path clears xHCI trust tokens, stops U-Boot USB only when a USB menu session was active, and leaves root-task to cold-start the high-BAR controller from Cohesix-owned mappings.
- The staged `boot.cmd` is pure Cohesix-owned USB cold boot: before `bootm` it switches input back to serial, clears stale `coh_xhci_*` trust tokens, runs one `usb stop` when a U-Boot USB input session was active, and deliberately discards U-Boot xHCI state instead of exporting stopped register seeds. Root-task may use the Linux-proven Pi 4 VL805 BAR0 `0x600000000` capture as bounded layout evidence, but capture-only state does not authorize fresh `DCBAAP`/ring/RUN publication. Fresh high-BAR ownership now requires the default HAL-owned BCM2711 EXT_CFG proof path: bind the PCIe/INTx sinks, mask/clear PCIe host sources, power the USB HCD domain through the VideoCore mailbox (`POWER_DEVID_USB_HCD=3`), validate live link/RC status, refresh the BCM2711 DMA/outbound MMIO windows even when link/RC already reports ready, run one bounded HAL-owned BCM2711 root-complex reset/window init if that status is missing, drain posted reset/window writes with same-block readbacks, wait through a conservative spin-backed U-Boot/PCIe CEM 100 ms post-PERST target plus bounded 100 ms link-poll target, then re-prove live link/RC status before any EXT_CFG tuple can authorize VL805 `01:00.0` (`1106:3483`, class `0x0c0330`, BAR0 translation, and COMMAND readback), and disable MSI for the poll-only lane. If that proof fails, the unseeded Cohesix-owned lane still returns before xHCI ownership writes. The image builder no longer supports an opt-in U-Boot xHCI ownership handoff export; `cohesix,xhci-mmio`, PCI COMMAND, stopped register seeds, and final handoff trust tokens are not staged by the boot script. The path does not emit USB trace breadcrumbs, force a handoff reprobe, record source labels, mirror capability/pre-stop/post-stop diagnostic snapshots, or derive a PCI config-space aperture from the xHCI BAR.
- Default USB-menu builds stay on the seL4-aligned `usbkbd` interrupt-polling baseline (`CONFIG_SYS_USB_EVENT_POLL=y`) so the HDMI/USB wizard matches the previously working Pi 4 input path; the explicit serial menu opt-out does not require U-Boot USB keyboard polling.
- The SD staging step also writes Linux comparison helpers `brcmfmac-dyndbg.cmdline` and `brcmfmac-dyndbg.sh` to the FAT partition. Use the `.cmdline` contents when booting a Linux known-good image to capture brcmfmac/MMC/SDHCI debug from module load, or run the shell helper after boot to enable the same dynamic-debug selectors through debugfs. These files are diagnostics only; the Cohesix cold-boot path does not append Linux bootargs to the seL4 handoff.
- `scripts/pi4-image-build.sh` deliberately does not run `scripts/pi4_trace_normalize.py`. The build script owns deterministic image staging/flashing and has no authoritative post-boot serial input; trace normalization is a post-capture evidence step. A future hardware-in-the-loop wrapper may call build, flash, serial capture, and normalization in sequence, but the staging script itself should remain artifact-only.
- `scripts/pi4_gate_proof.sh` is the hardware-in-the-loop wrapper for proof captures. By default it sends `smp activity` before the USB/Wi-Fi probes, sends `usb probe-kbd`, and sends a final `smp activity` after `netstats` so post-prompt owner-state proof is visible in the serial transcript. The default mode is a frontier sanity capture requiring `USB_GATE>=3`, `WIFI_GATE>=1`, a clean parsed serial stream (`SERIAL_CLEAN=yes`), no kernel halt (`BOOT_HALTED=no`), no seL4 timer entry (`TIMER_IRQ27_SEEN=no`), no U-Boot xHCI handoff evidence (`USB_BOOTLOADER_HANDOFF_SEEN=no`), and positive Cohesix-owned cold-boot evidence (`USB_COLD_BOOT_SEEN=yes`) before succeeding. `--require-usb-ready` is the full USB acceptance mode and requires `USB_GATE=10`, `USB_BLOCKER=none`, `USB_OLDGOOD_REPLAY=yes`, and `USB_OLDGOOD_MISSING=none`; `--require-wifi-ready` and `--require-ready` likewise require `WIFI_GATE=10`, `WIFI_BLOCKER=none`, `WIFI_OLDGOOD_REPLAY=yes`, and `WIFI_OLDGOOD_MISSING=none`. Use `--allow-summary-only` only for exploratory summaries that must not be treated as proof evidence.
- Optional Cohesix net-policy overrides mirrored into DTB `/chosen` by the staged boot script:
- `setenv coh_net_mode <off|static|dhcp>`
- `setenv coh_net_interface <wired|wifi|auto>`
- `setenv coh_static_ip <ipv4>` (mirrored into DTB `/chosen/cohesix,static-ipv4`; only applied when the effective mode is `static`)
- `setenv coh_static_prefix_len <1..32>` (mirrored into DTB `/chosen/cohesix,static-prefix-len`; only applied when the effective mode is `static`)
- `setenv coh_static_gateway <ipv4>` (mirrored into DTB `/chosen/cohesix,static-gateway`; optional and only applied when the effective mode is `static`)
- `setenv coh_wifi_ssid <ssid>` (mirrored into DTB `/chosen/cohesix,wifi-ssid`; used by the CYW43455 path when `coh_net_interface=wifi` or when `auto` prefers Wi-Fi; root-task accepts 1-32 printable ASCII bytes)
- `setenv coh_wifi_psk <psk>` (mirrored into DTB `/chosen/cohesix,wifi-psk`; used by the CYW43455 path for open/WPA2-PSK join; root-task accepts empty for open networks, 8-63 printable ASCII bytes for WPA2 passphrases, or exactly 64 ASCII hex digits)
- WPA2 passphrases are converted in root-task to the Linux-shaped 32-byte PBKDF2-HMAC-SHA1 PMK before `WLC_SET_WSEC_PMK`; 64-character hex values are decoded directly as that PMK.
- The staged boot script now hands the saved `coh_wifi_*` variables directly to `fdt set` without mutating or persisting escaped shadow copies, so repeated boots and policy-file writes do not grow backslashes or corrupt WPA2 credentials. If an older card reports `Wi-Fi credential handoff overflow`, clear the saved `coh_wifi_ssid` / `coh_wifi_psk` values once and re-enter them through the wizard.
- The staged `bcm2711-rpi-4-b.dtb` is padded to 128 KiB before flashing, so U-Boot can add `/chosen/cohesix,*` properties in place without `fdt resize`.
- `setenv coh_show_logo <0|1>` (controls whether the staged `boot.bmp` splash is displayed on HDMI before the menu; current staged default shows it for 1 second)
- The staged Pi 4 U-Boot build enables 24bpp BMP drawing, so the centered `boot.bmp` splash uses the same HDMI framebuffer path as `bmp display`.
- Pi 4 U-Boot now keeps `CONFIG_PREBOOT` on the seL4-aligned serial/video console path only; the HDMI wizard owns the first `pci enum; usb start` so boot no longer pays an unconditional duplicate USB-host bring-up before the menu. The default Pi 4 path still avoids a global scripted USB startup delay, but it keeps a targeted Apple `05ac:1006` keyboard-hub quirk in the U-Boot hub driver: a 250 ms post-config settle and a 5 s hub debounce timeout before downstream child probing.
- On first entry to the root menu, the staged `boot.bmp` copy of the Cohesix logo is shown centered for the configured 1-second splash delay; the wizard then prepares the menu/input USB session and draws the interactive menu on a cleared console.
- `ping ${serverip}`
- `fatwrite mmc 0:1 ${coh_policy_addr} cohesix.env ${filesize}` (only when explicitly persisting Cohesix policy)
- The staged `boot.cmd` copies these env vars into `/chosen/cohesix,*` on the staged DTB before `bootm`. If that DTB cannot be loaded or updated, the script aborts before handoff instead of silently booting with stale policy. Saved Cohesix policy persists across reboots via `cohesix.env`, but the manifest remains the build-time default and is never rewritten on the SD card.

## Milestone 26b Pi 4 network wizard checklist (as-built)
1. Build Pi 4 payload with the 26b policy-capable manifest:
- `scripts/pi4-image-build.sh --manifest configs/root_task_pi4_uboot_aarch64.toml`
2. At the U-Boot wizard, either:
- wait for `Continue with existing config` or `Boot with manifest defaults`, or
- choose `Configure networking` and walk the prompts:
  - `DHCP ON (automatic address)` or `DHCP OFF (static IPv4)`
  - `Wired Ethernet (GENET)` or `Wi-Fi (CYW43455)`
  - when `DHCP OFF`, enter `Static IPv4 address`, `Prefix length`, and optional `Gateway IPv4`
- when `Wi-Fi`, enter `Wi-Fi SSID` and optional `Wi-Fi PSK`
- rely on the runtime `[local-seat] ...` xHCI ownership breadcrumbs for current Pi 4 keyboard evidence; U-Boot contributes only the menu USB session before `bootm`, while runtime ownership is always Cohesix cold boot
- Pi 4 USB runtime is linked-runtime-only and cold-boot-only: U-Boot may provide menu input before `bootm`, but root-task ignores U-Boot xHCI handoff, stop-state, preserve-state, bootloader reset evidence, and Linux/U-Boot root-port captures as runtime authority. The active USB path is PCIe owner replay plus the linked `usb-local-seat` runtime, which owns fresh Cohesix xHCI rings, controller command/event proof, live root-port power assertion/sampling, current-boot root-port reset, HID enumeration, first report, and first-byte proof.
- USB Gate 1 now requires linked-runtime transport proof before PCIe/VL805 descriptor replay: each isolated driver TCB emits `DRIVER_TASK_IPC_BIND ... source=child-vspace-mapped-cap`, then the linked runtime must publish `runtime-entry-ready` followed by either `runtime-recv-ready` or sparse `runtime-poll-ready` progress before root sends bounded descriptor/init turns. A capture with no runtime progress after the IPC-bind breadcrumb is a linked-runtime admission failure; a capture stopped at `runtime-recv-ready` or `runtime-poll-ready` is a root-to-runtime command delivery failure, not an xHCI or keyboard failure. Newer linked runtimes also emit `runtime-ring-read-begin` once before the first uncached shared-ring read, `runtime-poll-ready` when the child intake loop is alive but has not observed a fresh shared-ring sequence, `runtime-poll-begin` immediately before endpoint polling for reply-cap commands, and `runtime-reply-pending` when a non-one-way command is visible without a reply cap. PCIe-root descriptor replay and engine-init keep the same request active across three bounded timeout turns so the Gate 2 owner command remains stable while the child reads the sequence-last shared ring first and polls the endpoint only for commands that require a reply cap. Runtime command-ring, bus-owner-ring, and root-shared descriptor/payload pages use volatile loads/stores plus barriers in the linked runtime; root additionally cleans staged descriptor/payload bytes and command/completion records before sequence publication, and invalidates completion/progress records before consuming replies. Device DMA buffers keep their explicit clean/invalidate path. Root preserves the child-owned progress marker across submits, so timeout lines identify both the active request and the last runtime marker instead of erasing child evidence.
- if the cold-boot runtime path still freezes during the first controller ownership write, the exact-issue surface now reports the specific wedged store (`pre-run-config-store-wedged`, `pre-run-dcbaap-low-store-wedged`, or a later ring/ERST edge) rather than collapsing all failures into a generic controller edge.
3. Optional persistence:
- choose `Save current settings and reboot` or `Save settings and reboot` to persist only the Cohesix policy fields into `cohesix.env`.
4. Boot and confirm policy evidence:
- `[net-policy] source=manifest ...`, `[net-policy] source=dtb ...`, or `[net-policy] source=dtb rejected reason=<reason> ...`
- `manifest.hw.network.mode=dhcp`
- `manifest.hw.network.interface=auto`
- `manifest.hw.networking=enabled-dhcp`
- for the manifest-default boot with no saved Wi-Fi credentials, `[net-console] pending-dhcp ... active=wired ...` followed by `[dhcp] lease bound ...`
- for wizard-selected `mode=dhcp`, `[net-console] pending-dhcp ...` followed by `[dhcp] lease bound ...` and then `[net-console] ready ip=<lease-ip> ...`
- for wizard-selected `mode=static`, `[net-console] init: bringing up backend=... mode=static interface=... ip=<static-ip>/<prefix> ...`
- if the staged DTB carries an explicit invalid override such as `wifi-psk-too-short`, root-task now rejects that override, emits `[net-policy] source=dtb rejected reason=<reason> ...`, and disables net-console with `invalid net config: dtb override rejected (<reason>)` instead of silently falling back to the manifest-selected backend.
- when saved wizard settings are used after reboot, root-task must not print `[boot] dtb locate skipped/failed: bootinfo extra truncated`; that message indicates the DTB handoff was lost before policy resolution and is a regression.
- for wizard-selected Wi-Fi or wired Pi 4 local-seat boots, driver-task bootstrap creates the selected-only active TCB set and leaves `DRIVER_TASK_BOOT ... started=yes` breadcrumbs; Wi-Fi selects SDIO plus CYW43, while wired selects GENET. `DRIVER_TASK_SELECTED` and `DRIVER_TASK_ACCEPTANCE` include `active_net=cyw43|genet|none`, and owner-state proof requires serial, USB, HDMI, PCIe, and only the selected network hot paths (`cyw43-wifi` plus `sdio-host` for Wi-Fi, or `genet-nic` for wired). Runtime-init service proof remains red until the deferred descriptors replay and return hardware progress. Mapped isolated shared rings may already make `pointer_free_ipc=yes`; when that proof is present for Wi-Fi boots, root-task records the deferral, publishes only the startup banner, starts SDIO/CYW43 descriptor replay with `[net-console] deferred resume reason=before-root-prompt action=start-wifi`, then publishes `Cohesix console ready` / `cohesix>` after the replay returns ready, pending, or fail-closed so noisy descriptor startup cannot hide an interactive prompt. Host-EAPOL or DHCP waits still cannot hold the serial shell. If physical-Pi proof is insufficient, root emits `[net-console] deferred resume skipped reason=driver-task-net-runtime-unproved action=serial-diagnostics-only`, publishes the prompt with compact blockers, and does not run a hidden synchronous Wi-Fi replay behind the shell. CYW43 firmware-transfer recovery preserves the already-prepared SDIO HAL/WL_ON resources and retries the retained firmware stage through the existing SDIO owner state. Pi 4 display bring-up is earlier than USB: the framebuffer hint is published before driver-task bootstrap, `hdmi-text` clears the whole mapped framebuffer at Cohesix HDMI start, then paints descriptor-time linked-runtime diagnostics after framebuffer resources validate. A successful linked `SubmitFrame` is sufficient HDMI owner-state proof; empty HDMI engine-init no-reply cannot block first-frame submission. The post-prompt settle path may retry linked HDMI and USB only for remaining frontier work; queued serial or HDMI output is not physical input and must not delay local-seat USB attach. If the USB runtime already has an active command, local-seat attach emits one `prompt-settle attach deferred reason=usb-runtime-active` summary and retries after the normal quiet window. HDMI must not wait for USB keyboard attach or an unproved local-seat dependency. Once the linked display attaches, root owns canonical HDMI terminal state and submits bounded chunks through `hdmi-text`: the prompt and typed USB bytes remain on the same row, command output closes the open prompt row before printing, tail output scrolls like a serial terminal, and USB up/down arrows request bounded history viewport redraws. Snapshot redraws first send `ESC[H` plus `ESC[J` to clear the linked HDMI text surface before repainting from root-owned scrollback, derive the stable viewport row count from the same framebuffer safe-area geometry as the linked runtime, split that full viewport across multiple bounded HDMI service turns when required, clear every rendered row to the physical right edge with `ESC[K`, clear below the final rendered row with `ESC[J`, and omit a trailing newline on the final row so the redraw does not scroll itself or leave the cursor after padding spaces. The linked runtime treats the framebuffer as an overscan-sensitive surface and clips normal HDMI text clear, scroll, glyph, and pixel writes to a whole-character safe rectangle derived from a two-percent per-side inset, so the visible text surface is about 3-5 percent smaller than the full mode after character alignment. If linked HDMI does not reply, high-impact frame submission records `HDMI_FRAME_SUBMIT` / `HDMI_FRAME_PROGRESS` telemetry, queued routine bytes are superseded by one pending canonical redraw instead of raw stale-payload replay, routine mirroring defers while the HDMI ring is active, and serial remains the complete diagnostics channel until linked frames prove completion. USB uses the linked PCIe descriptor-adoption proof after HAL has prepared the live BCM2711/VL805 tuple; a separate PCIe engine-init no-reply must not wedge USB before xHCI. Failed PCIe owner-state still blocks USB with `blocked-pcie-owner-state`, but descriptor replay plus HAL-prepared VL805 proof is the expected owner prerequisite. USB keyboard polling remains bounded after the prompt: no-reply background USB polls suspend with `[local-seat] linked USB runtime keyboard poll suspended contract=usb-local-seat source=linked-runtime reason=driver-task-no-reply action=serial-shell` so serial remains live for diagnostics. After USB polling is armed and proof succeeds, serial and USB keyboard input must both remain live and feed the shared root-console parser concurrently; post-first-byte no-reply recovery may be retried after each bounded no-reply window if the prior recovery turn also failed to reply. `usb status` separates `first_byte_source=local-seat-queue-diagnostic` parser ingress from `first_byte_source=linked-runtime-hid` acceptance proof, and only the linked-HID latch can close Gate 10. Prompt-side `wifi diag`, `nettest`, and USB diagnostics report the boot-attempt state without waiting for hidden services; DHCP/data stay blocked until the selected NIC runtime proof returns. USB and Wi-Fi diagnostics include cached `linked_runtime_progress` rows when a ring call timed out, and linked engine-init resource checks now publish descriptor, hot-path, service-dispatch, total, MMIO, DMA, shared-page, framebuffer, forbidden-window, pointer-free bus-link, success-only completion-publish, SDIO adoption, SDIO first-MMIO/reset submarkers, and xHCI 64-bit register submarkers so the next capture maps descriptor replay, resource validation, hardware init, HID, DHCP, `nettest`, and `netstats` blockers to their current ten-gate frontier while faulting turns preserve the last meaningful phase. Shared-ring command, progress, completion, and CYW43-to-SDIO owner payload pages are uncached runtime mappings and use volatile access plus barriers; runtime cache maintenance is reserved for descriptor-declared device DMA buffers. Generic engine-init timeouts clear the active slot after emitting progress; explicit USB enumeration/local-seat, PCIe prerequisite, SDIO descriptor replay, and SDIO engine-init paths keep bounded prompt-side resume semantics so an in-flight linked-runtime hardware turn is not overwritten before it returns ready or reaches its finite no-reply limit. A trace that stops at `wifi-net-console-pending-before-root-console` before the proof decision is known is still blocked and must normalize as `WIFI_BLOCKER=boot-waiting-for-wifi`, not `none`.
- when net-console never comes online, the serial/local-seat `nettest` and `netstats` commands must no longer collapse that state to a bare `detail=net-disabled`; they now preserve the boot-time init detail as `detail=net-disabled cause=<net-console init detail>`, so a failed CYW43 bring-up can still be diagnosed after the shell is live.

## Bootloader/HAL ownership boundary
- Bootloader-owned (pre-handoff): Pi firmware + U-Boot setup, media loading, pre-boot env/network commands.
- Cohesix-owned (post-seL4): HAL-backed runtime device access only (UART, local-seat paths, attestation plumbing, network handoff points).
- Root-task runtime code must not call bootloader/firmware services directly after seL4 entry.
